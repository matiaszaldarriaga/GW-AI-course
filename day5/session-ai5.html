What I am going to show

  
A paper, published as a repository


  
The paper is Zaldarriaga & Sato-Polito, Anisotropies in the
    PTA gravitational wave background, and it was written by the agents. It is the
    same paper day 4's six jobs were measured against: day 4 asked a team to
    derive these results and scored it against the paper's registry of stamped
    numbers. Today opens the same repository from the other end and shows what it took
    to publish them.


  
A standard part of reading a paper is working out what the claims are and what the
    evidence is. In this repository that is not left to the reader: it is written down,
    once, in a form both a person and an agent can read, and a script checks that the
    paper, the code and the data still agree with it. That is what is available now and
    was not before, and it is the one idea of the hour. The files below are on screen
    in this order, one at a time.

check 7 of 10

      
Every displayed \dataref
        “literal agrees with its registry value at the literal's displayed
        precision”. Not that the key exists — that is check 6 — but
        that the digits printed on the page are the digits in the registry, to the
        precision the paper chose to print. [src:q_check_7]

Three of the ten only make sense in the public layout,
        and run against another tree “each reports itself as skipped rather than

        0 when the paper, the code and the data agree.”
        [src:q_check_skip, q_readme_pass]

    

  


  
The rest of the list, in the docstring at the top: every
    data_ref in the skeleton resolves to a file or a bib key;
    every number key the skeleton names is in the registry; every figure has a source
    script and a PDF; every \genby names a file that exists;
    every path-like token in every shipped text file resolves; the citation file parses;
    and every deposited array names a producer that ships. None of it is a check on the
    physics. All of it is a check that the paper still says what the code and the data
    say, and it is the same kind of check as the one waiting in your directory
    c/.

README.md — scroll to Reproducibility
      

    
the file

  


  
“That is not the same as byte equality across machines”, it says first,
    and then draws the lines. [src:q_readme_not_bytes]


  
    
    
  1. Bitwise, demonstrated. “data/paper_numbers.json regenerates
      byte-identically, and so do both table sidecars”.
      [src:q_readme_bitwise]
    2. 
    
  2. Bitwise, with one caveat. “the eleven figure PDFs regenerate
      raster-identically — zero differing pixels at 200 dpi — but not
      byte-identically, because matplotlib stamps the wall-clock time into /CreationDate
      and its own version into /Producer”. And the one-line fix: “Set
      SOURCE_DATE_EPOCH to any fixed value and, for a fixed matplotlib version, the PDFs
      become byte-identical too”. [src:q_readme_raster,
      q_readme_raster_fix, rel_readme_raster_dpi]
    3. 
    
  3. Within a stated tolerance, and measured. The tests compare at
      1e-12 of each array's own scale, and that number was measured rather than chosen:
      “Running the suite under a second OpenBLAS build (0.3.25/OpenMP against the
      reference platform's 0.3.21) with every Python package version held identical, the
      worst disagreement over every reference array was 1.1e-14 of the array scale —
      one hundred times inside the tolerance.”
      [src:q_readme_openblas, rel_readme_test_tol,
      rel_readme_openblas_worst]
    4. 
    
  4. Within tolerance, not bitwise. The Monte Carlo products:
      “distribution percentiles from independently drawn realizations agree only to
      Monte Carlo error”, and “Every number quoted in the paper is rounded well
      inside that.” [src:q_readme_mc]
    5. 
    
  5. Not claimed anywhere: “that the deposited arrays can be
      reproduced byte-for-byte on a different platform. The deposited arrays are what the
      paper used; the pipeline is how they were made.”
      [src:q_readme_not_claimed]
    6. 
  


  
Nobody wrote a section like that by hand before, because nobody could afford to:
    every sentence in it is a run in a fresh environment against the deposited arrays,
    with the disagreement measured. That is the “available now” claim of the
    hour, and it is checkable by opening the file rather than by taking my word for it.

the hook

      
Two hundred lines. It runs at Stop
        — the moment the agent decides it is finished — checks what was left
        on disk, and if a figure or a number has no record it exits non-zero, which puts
        its message into the conversation as a new turn. It prints only the
        .md for whichever checks failed.
        [src:scaffold_hook_lines]

    

  


  
Why a hook at all, when the skill already says what to do: “In a long run the
    agent may never load the skill. The hook runs whether or not it did, and that is what
    it is for.” [src:q_hook_why] Add a check, write its
    .md, and both routes get it. Nothing in any of these files
    mentions the paper, the physics or a library — the build of this page refuses if
    one does — and the same three files would sit unchanged in a directory about
    something else.


  
The lining-up with the release is not a metaphor. The skill is what
    paperclaims.sty is: the convention a piece of writing is
    held to, loaded where the writing happens. The hook is what
    check_provenance.py is: the check that runs before the thing
    is allowed to be finished. And the record your agent writes,
    provenance/claims.yaml with its statements, evidence and
    numbers, is the skeleton at the top of the release with one paper's worth of claims
    taken out and one afternoon's put in.

What the three cells measure

This is the real gap. With nothing written down for it,
        the agent computes the right number, checks it a second way, says so, and the
        number lives in a chat message. With either of the two things in the directory,
        the same number is in a file with its function, its library call and its

Not a quality difference. It is when the instruction
        arrives — up front, or at the door — and both land: the two

        calls. In b/ the hook never had to do anything; in

        cell_c_hook_fires]

    

  


  
So: the skill is the normal route, and the hook is the one that still works when the
    skill does not get loaded. That is what the two cells demonstrate, in their own
    transcripts, rather than what I am asserting. In a session of one task the skill gets
    loaded at the start and the hook is idle; the case the hook exists for is the long
    run where it does not, and c/ is that case made to happen on
    purpose.
