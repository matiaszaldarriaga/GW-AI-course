# Reproducibility

What a fresh clone of this repository does NOT include, and how to rebuild each missing piece. Everything in this project that is not tracked in git MUST be listed here with a command (or command sequence) that regenerates it.

## Principle

> Any file or directory that exists locally but is not tracked in git MUST have a reproducibility entry in this page. Creating new untracked content includes adding its entry here.

### Amplitude normalization (`--target-hc`, since 2026-06-22)

`run_population_analysis.py` and `run_power_anisotropy.py` now **calibrate the
velocity-dispersion-function normalization $\phi_\sigma$ per model** so that
every $\varepsilon$ shares the same observed mean amplitude
$\sqrt{\langle h_c^2\rangle(1\,{\rm yr}^{-1})} = 2.5\times10^{-15}$ (helper
`gwb_sources.population.calibrate_phi_sigma`). Because $\langle h_c^2\rangle
\propto \phi_\sigma$ (linear; $h_s^2$ is independent of $\phi_\sigma$), this is
an exact one-step rescaling. Calibration factors $\kappa$ (relative to the
Sato-Polito fiducial $\phi_\sigma = 2.611\times10^{-2}$): **13.26** ($\varepsilon=0.20$),
**6.14** ($\varepsilon=0.38$), **0.72** ($\varepsilon=0.66$). The npz now stores
`kappa`, `target_hc`, `phi_sigma`.

- Default (matched): `python scripts/run_power_anisotropy.py --eps 0.66`
- Custom target: `... --target-hc 2.4e-15`
- Legacy unmatched (old fiducial $\phi_\sigma$, all models): `... --no-match`

Changing $\phi_\sigma$ changes the Poisson source counts, so it changes the
anisotropy statistics ($p_1$, $N_{\rm eff}$, $C_1/C_0$): the low-$\varepsilon$
models become much less anisotropic. All Section III/IV figures and tables
depend on this calibration.

## Sampled-property Monte Carlo sidecar

### Authoritative schema-v2 production (2026-08-11)

The old `new_montecarlos_codex/results/` directory is immutable comparison
input. Corrected products go to the versioned sibling
`new_montecarlos_codex/results_full_moment_v2/` and require schema version 2.
For each epsilon model, run one common power Monte Carlo and derive the compact
population product from it without another draw:

```bash
for spec in 0.20:eps020 0.38:eps038 0.66:eps066; do
  eps="${spec%%:*}"
  tag="${spec##*:}"
  conda run --no-capture-output -n gw_pta python \
    new_montecarlos_codex/run_new_power_anisotropy.py \
    --eps "$eps" --nrel 10000 --nside 8 --n-brightest 100 --seed 42 \
    --individual-threshold 500 --tail-grid-size 4096
  conda run --no-capture-output -n gw_pta python \
    new_montecarlos_codex/run_new_population_analysis.py \
    --eps "$eps" --nrel 10000 --n-top 20 --seed 42 \
    --individual-threshold 500 \
    --from-power "new_montecarlos_codex/results_full_moment_v2/sampled_power_anisotropy_${tag}.npz"
done
conda run --no-capture-output -n gw_pta python \
  new_montecarlos_codex/generate_sampled_c1c0_distribution.py
conda run --no-capture-output -n gw_pta python \
  new_montecarlos_codex/validate_full_moment_products.py
```

The schema stores direct $Q$, full $S_2$, $Q^2/S_2$, direct dipole, complete
source ledger and remainder identities, positive maps, seeds, tail errors, and
producer metadata. Corrected consumers reject the old incomplete schema.

The remainder of this section records the superseded 2026-07 sidecar workflow
for historical comparison; its `bulk_pixel_mode=mean` and partial-ledger
contract must not be used as corrected production.

New (2026-07-13): `new_montecarlos_codex/` contains a separate workflow for
testing and eventually replacing the paper's deterministic per-`(f,M)` source

Important files:

- `new_montecarlos_codex/run_quick_comparison.py` writes

```bash
for eps in 0.20 0.38 0.66; do
  conda run -n gw_pta python new_montecarlos_codex/run_new_population_analysis.py \
    --eps "$eps" --nrel 10000 --n-top 20 \

conda run -n gw_pta python new_montecarlos_codex/generate_comparison_report.py
```

The power files intentionally use `bulk_pixel_mode=mean`.  An initial
`bulk_pixel_mode=moment` attempt clipped negative per-pixel Gaussian bulk
fluctuations to zero, which inflated bulk map power and suppressed the
brightest-source fractions in the power products.  The corrected production
files use aggregate bulk mean maps and exact sampled bright-bin ledgers.

The brightest-source ledger remains exact only for bins selected by
`individual_threshold`; aggregate bulk bins do not contribute candidates to
`brightest_n_strains`, `brightest_h2s`, or top-source exclusions.  The
threshold 100/500/2000/5000 quick reports in
`new_montecarlos_codex/reports/` document convergence at the representative
paper frequencies.

The separate historical threshold reports did not hold `Nrel` and the epsilon
set fixed. The controlled replacement is:

```bash
conda run -n gw_pta python new_montecarlos_codex/run_threshold_sweep.py
```

It writes `reports/threshold_convergence_fixed.md` with `Nrel=2000`, seed 42,
all three epsilon values, and frequency indices 0/3/15 at every threshold.
Threshold 500 is generally within about 6% of threshold 5000 in the median;
the largest case is epsilon 0.20 at 0.085/yr (median 9% low, 95th percentile
17% low), consistent with the expected conservative ledger bias.

## arxiv TeX source packages

### What is not tracked

For each of the 9 arxiv papers, `references/<arxiv_id>/` contains a tracked `README.md` (with the paper title, authors, bib key, and which paper sections cite it), but the TeX source itself is excluded. Each directory holds 1–5 MB of tex after fetching. This split keeps the list of referenced papers visible in a fresh clone while avoiding redistribution of third-party copyrighted material.

### How to restore

```bash
bash scripts/fetch_references.sh              # download all 10
bash scripts/fetch_references.sh 2602.16808   # one specific ID
```

The script requires `curl` and `tar` (standard on macOS and Linux). It sleeps 2 s between requests to respect arxiv rate limits. Re-running is safe: existing tarballs are not re-downloaded.

### Review annotations and the decision console (2026-08-12)

Every review comment in the draft is a `paperclaims` macro carrying a stable
id as its first argument — `\mzcomment{MZ-05}{...}` (MZ's own read),
`\gscomment{GS-04}{...}` (Gabriela's), `\ccnote{D-12}{...}` (agent-raised).
Ids are assigned in document order and print inside the tag, so a block in
`main.pdf` matches a row in the console. All three vanish under
`\usepackage[final]{paperclaims}`.

Two generated artifacts are tracked, and both rebuild from the `.tex`:

```bash
# 1. stamp any new comment with the next free id, and export the inventory
#    (id, kind, file, line, section, printed page, LaTeX body)
python paper_v2/scripts/number_paper_comments.py     # -> paper_v2/data/comment_inventory.json
# 2. render the console from the inventory + the authored resolutions
python paper_v2/scripts/build_decision_console.py    # -> wiki/reviews/paper_v2_decisions.html
```

Step 1 reads the printed page of each id back out of `main.pdf` with
`pdftotext`, so rebuild the PDF first if pagination has changed. The authored
half — title, suggested resolution, options — lives in
`paper_v2/data/decision_items.json` and is edited by hand; the complaint text
is never copied there, it is converted from the `.tex` at build time so the
console cannot drift from the PDF.

## Public release (`release/`, built 2026-08-12)

`release/` is the public-ready mirror of the `paper_v2` pipeline, modelled on
`../DESI-w0wa/release`. It is a **derived tree**: assembled by explicit copy
from an allowlist and never hand-edited. If something in it is wrong, the fix
goes in the working tree — or in the assembly tables — and the release is
re-cut:

```bash
conda run -n gw_pta python scripts/assemble_release.py
```

That wipes `release/` (preserving any `.git`), re-copies, renames, rewrites
paths, regenerates the reader-facing files, and re-runs the verification greps.
The two scripts that do it, `scripts/assemble_release.py` and
`scripts/_release_files.py`, stay in the working tree and never ship.

**Layout map.** `paper_v2/{main.tex,sections,paperclaims.sty,references.bib,figures}`
→ `paper/`; `paper_v2/scripts/*.py` → `scripts/`; `new_montecarlos_codex/`
producers plus `scripts/run_sqrtSH_realizations.py` → `scripts/mc/`;
`gwb_sources/` → `src/gwb_sources/`; `paper_v2/structure/*.yaml` → `structure/`;
the small data products → `data/`.

**One data root.** Every producer and every consumer in the release resolves
data through `PTA_DATA`, defaulting to `<release>/data`. This is what closed the
audit's producer/consumer mismatch.

**Self-checking rewrites.** Each path rewrite declares how many occurrences it
must replace and the assembly aborts on a mismatch, so an edited source file
fails loudly instead of shipping a broken path.

**What is committed in the release** (7 files, enough to build the paper and 4
of the 11 figures): `paper_numbers.json`, `detection_penalty_mc.json`,
`cw_limit_comparison.json`, `15yr_cw_3d_limits_v4.npz`,
`sampled_c1c0_distribution_eps066.npz`, `sqrtSH_realizations_lmax3.npz`,
`sqrtSH_low_moments_convergence.npz`.

**What is deposited.** The six production arrays (~15 GB) go to Zenodo, not to
git — the three `sampled_population_analysis_eps*.npz` at 0.31 GB each already
exceed GitHub's 100 MB per-file limit, and the three
`sampled_power_anisotropy_eps*.npz` are 4.9 GB each. `release/data/ZENODO.md`
is the manifest: size, SHA-256, schema name and version, seed, wall time, peak
RSS and the exact producing command line for each, plus the record metadata.
`release/scripts/fetch_data.sh` downloads and verifies them; its `ZENODO_DOI` is
a placeholder until the record exists, and `bash scripts/stamp_doi.sh <doi>`
stamps the real one into the generator and re-cuts the release so README,
`CITATION.cff` and `fetch_data.sh` cannot disagree.

**Seven of the eleven figures need the population arrays**, so "rebuild every
figure from committed data" is not attainable; `release/scripts/make_all_figures.py`
builds what the present data allow and names what it skipped and why. No figure
script reads the 4.9 GB power cubes at all — those are needed only by one
analytic cross-check inside `compute_paper_numbers.py`.

**The reproducibility claim, as measured** (fresh environment, every Python
package version identical to the reference platform, a *different* OpenBLAS
build — conda-forge 0.3.25/OpenMP against the reference 0.3.21):

| artifact | result |
|---|---|
| `data/paper_numbers.json`, both table sidecars | byte-identical |
| the eleven figure PDFs | raster-identical (0 differing pixels at 200 dpi); bytes differ only in matplotlib's `/CreationDate` and version string — byte-identical with `SOURCE_DATE_EPOCH` fixed |
| `tests/reference_data/` comparisons | agree to 1.1e-14 of each array's scale |

"Bitwise" is used in the release README only for the first row. This is also why
`environment.yml` now pins exact patch versions and why three test assertions
moved from `assert_array_equal` to a `1e-12`-of-scale tolerance — the BLAS
build, not the package versions, was the variable.

Full record: `intents/paper-v2-release-build_receipt.md`; the steps left for MZ
(GitHub, Zenodo, DOI, tag) are in `intents/release-handoff.md`.

## Zenodo deposit

Every schema-v2 product records, inside the file, the script that produced it,
and the population products additionally record the power product they were
derived from. Those strings are working-tree paths
(`new_montecarlos_codex/run_new_power_anisotropy.py`,
`new_montecarlos_codex/results_full_moment_v2/sampled_power_anisotropy_eps020.npz`),
which no reader of the public release can follow. The 2026-08-13 release audit
raised this as F03, together with `release/data/ZENODO.md` advertising two
schema names — `pta_anisotropy.sampled_power` and
`…sampled_population` — that no file actually carries. Every deposited array
carries the one schema `pta_anisotropy.sampled_full_moment`; `product_kind`
is what separates a power run from the population product derived from it.

```bash
conda run -n gw_pta python scripts/build_zenodo_deposit.py     # ~90 s, ~16 GB
conda run -n gw_pta python scripts/assemble_release.py         # publish the new hashes
```

`build_zenodo_deposit.py` writes `zenodo_deposit/*.npz`: copies of the six
production arrays in which the `producer` field is rewritten to the release
path (`scripts/mc/run_new_power_anisotropy.py`) and
`derived_from_power_product` is reduced to a bare file name, because the data
root is configurable. Nothing else changes. The rewrite (`scripts/_npz_provenance.py`)
copies members inside the zip rather than reloading the arrays: the large
members are stored uncompressed, so every science array streams through
untouched and none of them is ever held in memory. Verified after the first
build: all 103 (power) and 93 (population) members compare equal, and only
`producer` and `derived_from_power_product` differ.

Rewriting those strings does change each file's bytes, so the script measures
the copies and writes `intents/zenodo_deposit_manifest.json`;
`scripts/_release_files.py` reads it and publishes those sizes and SHA-256
values in `release/data/ZENODO.md`, `release/README.md` and
`release/scripts/fetch_data.sh`. **Upload `zenodo_deposit/`, not
`new_montecarlos_codex/results_full_moment_v2/`** — the masters keep their
working-tree provenance and are left alone.

The same substitution is applied to the two committed NPZ products during
assembly (`assemble_release.relabel_arrays`), so `release/data/` and the
deposit tell the same story. `release/scripts/check_provenance.py` check 10
enforces it: every array in the data root must name a producer that exists in
the release and carry the schema the manifest declares.
