Day 1

Chat, agent, harness

Chatbot

Text in, text out. It cannot see your files, run anything, or check itself. Whatever it says about your data is a guess about your data.

Agent

The same model, in a loop, with tools: read a file, write a file, run a command, look at the output, decide what to do next. That loop is the entire difference.

Harness

What is around the agent: permissions, project instructions, skills, hooks, subagents (agents the agent launches), jobs. The part you configure — and the part that makes it yours. Each piece gets its own day this week.

Two modes, and you will use both:

Interactive. You watch, you steer, you interrupt.

This is what you are doing while the room is running.

Headless / jobs. Fire it at a bounded deliverable and walk away. claude -p, codex exec, or a whole team of agents on a job.

Day 4 is the one that does this at scale.

Context

Everything the model can see right now — your instructions, the files it has read, the commands it has run and their output — is one flat block of text. It is finite.

What fills it. Long files. Verbose command output. A 200-line traceback. A PDF. Twenty rounds of trial and error.

What happens when it fills. It gets summarised. Detail is lost, and you do not choose which detail. Quality degrades in a way that is hard to notice from the outside.

Look at it. Both harnesses will tell you how full it is and what is taking up the room:

Claude Code
/context     what is in it, and how full
/compact     summarise and keep going
/clear       throw it away and start clean
Codex CLI
/status      session and token usage
/compact     summarise and keep going
/new         a fresh conversation

The practical skill is not writing clever prompts. It is deciding what deserves to be in context: keeping tasks bounded, starting fresh when the thread is spent, and writing things to disk rather than carrying them in the conversation.

Run /context now, and again when your run finishes. When it is nearly full, believe less of what you read.

Every session starts cold

Close the terminal and it is gone. Tomorrow the agent knows nothing about today — not the conventions you agreed, not the bug you found, not why you rejected the obvious approach.

There is exactly one fix: write it down, in the project, in a form the agent will read next time.

Project instructions. CLAUDE.md / AGENTS.md at the root. Conventions, layout, what not to do. Read automatically at every start.

A record of the work. What was tried, what it cost, what the answer was — the receipt that sits beside the code, saying it ran, on what date, in which environment, and how many checks passed. An exercise without one is a plan.

A useful test: if you were hit by a bus, could a stranger — or a fresh agent — pick this project up from what is on disk? That is the same question, and it has been good practice since long before any of this.

Day 4

More than one of them

day 4

Teams and roles — a lead that plans and assigns, workers in parallel, and a verifier. Each with its own model and its own depth: put the verifier on a different model family from the workers and the check stops being the same model marking its own homework.

day 4

An independent verifier — and the question of whether what it finds ever reaches the round that has to act on it. Read reports/ and transcript/, not the deliverable.

day 4

Rounds — a bounded run that stops and hands the decision back. The budget is an input the lead plans against, not just a cost; a run can always be resumed, so what it dropped for lack of room should be written down rather than lost.

day 4

Steering — job say while it runs, job resume, job freeze. Check that a direction arrived; it is read at the start of a round and not before.

day 4

Skills — a procedure written down once, loaded when it is relevant. It is why a fresh session knows the tool exists at all: install puts the same SKILL.md into both harnesses, and cloning without it does nothing.

Day 5

Written down for the agent to read

day 5

Hooks — a command the harness runs at a named moment, whether or not the agent thinks of it. Day 5's fires at Stop, when the agent decides it is finished: it checks what was left on disk, and a non-zero exit puts its message into the conversation as a new turn, so the agent is not finished after all. A skill is loaded when the session thinks it applies; a hook runs regardless, which is what it is for. Both tools have the event, and Codex will not run a hook you have not trusted in /hooks.

day 5

A paper written for a machine to read — a repository whose claims.yaml states the thesis and one record per claim with its evidence named, whose prose carries a key beside every number, and whose check_provenance.py refuses the build when the paper, the code and the data stop agreeing. What a reader used to reconstruct by guessing, stated once, and checked.

day 5

The same idea in your own directory — the convention in .md files, written once; a skill that points at them; a hook that checks the result and, on failure, serves the .md that applies. Nothing restated. Add a check, write its .md, and both routes get it.
